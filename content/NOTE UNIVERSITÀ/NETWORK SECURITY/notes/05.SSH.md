SSH sta per *Secure shell* ed è un protocollo per connetersi ad una macchina remota in maniera sicura in una rete non protetta, sostituisce vecchi protocolli come Telnet, rlong, RSH e così via. SSH, rispetto a questi protocolli, non spedisce le informazioni in chiaro, infatti erano soggetti con un banale attacco di man in the middle con un packet sniffer

### Struttura SSH

SSH è organizzato su tre protocolli che lavorano sopra a TCP

![[Pasted image 20251103135147.png]]

- **Transport layer protocol**
	fornisce autenticazione server che avviene a livello di traporto. Questo protocollo si basa sul server che processa le coppie di chiavi pubbliche e private. Si suppone quindi che ogni host ha le sue chiavi. È anche possibile che più host abbiamo lo stesso *host key*. In ogni caso durante lo scambio di chiavi la *server host key* è usata per autenticare l'identità all'utente. Per far si che sia possibile questo, il client deve avere a priori a conoscenza la chiave pubblica *host key* del server. Possono essere usate due modelli:
	- il client ha un database locale che associa ogni *host name* con la corrispondente *host key* pubblica. Questo metodo non richiede quindi nessuna infrastruttura centralizzata amministrata e nessuna coordinazione di terze parti
	- L'associazione tra *host name* e *to key* è certificato dalla CA

	Per prima cosa si instaura una connessione TCP dal client al server. Questa connessione è fatta dal protocollo TCP e non fa parte del transport layer protocol. Una volta che la connessione è stabilita, il client e il server iniziano a scambiarsi dei messaggi e dati dentro dei pacchetti che verrano messi nel *data field* di un segmento TCP. - **User authentication protocol**
	Questa parte fornisce i metodi con cui l'utente si autentica al server. Sono sempre usati 3 tipi di messaggi. 
	1. string user name
	2. string service name
	3. string method name
	
	L'user name è l'identità che dice di essere al server, il service name è la cosa che il client sta facendo richiesta di accesso, mentre il method name è il metodo disposto da usare per l'autenticazione in questa richiesta. Lo scambio di messaggi tra client e server è il seguente

	4. Il client invia un messaggio `SSH_MSG_USERAUTH_REQUEST` con un metodo richiesto di _none_ (nessuno).
	5. Il server verifica se il nome utente è valido. Se non lo è, il server restituisce `SSH_MSG_USERAUTH_FAILURE` con il valore di successo parziale (partial success value) impostato su _false_. Se il nome utente è valido, il server procede al passo 3.
	6. Il server restituisce `SSH_MSG_USERAUTH_FAILURE` con un elenco di uno o più metodi di autenticazione accettabili da utilizzare.
	7. Il client seleziona uno dei metodi di autenticazione accettabili e invia un `SSH_MSG_USERAUTH_REQUEST` con il nome di quel metodo e i dati specifici richiesti dal metodo. A questo punto, può esserci una sequenza di scambi per eseguire il metodo.
	8. Se l'autenticazione ha successo e sono richiesti più metodi di autenticazione, il server procede al passo 3, utilizzando un valore di successo parziale impostato su _true_. Se l'autenticazione fallisce, il server procede al passo 3, utilizzando un valore di successo parziale impostato su _false_.
	9. Quando tutti i metodi di autenticazione richiesti hanno successo, il server invia un messaggio `SSH_MSG_USERAUTH_SUCCESS` e il Protocollo di Autenticazione è terminato.
	Questo protocollo usa 3 metodi di autenticazione
	- **public key**
		
	- **password**
		
	- **hostbased**
		

- **Connection protocol**
	questo protocollo consente di fare multiplexing di canali di comunicazioni logici in una singola sessione SSH. Il protocollo gira sopra al protocollo SSH transport layer e assume che viene utilizzata una connessione con autenticazione sicura. Questa connessione viene chiamata **tunnel**, il quale permette di creare canali di comunicazioni logici. Sono "vie" del tipo che si aprono, si utilizzano e si chiudono (non seguono altri flow). Tutti i tipi di comunicazione usando SSH sono supportate usando canali separati. I canali hanno le seguenti caratteristiche
	- possono essere aperte da entrambi i lati (comunicatori)
	- per ogni canale, ogni lato associa un numero unico al canale
	- i flow dei canali sono controllati da un meccanismo di finestre
	- nessun dato viene spedito se non prima di un messaggio ricevuto per indicare che lo spazio della finestra sia disponibile

Quando entrambi i lati vogliono aprire un nuovo canale nel tunnel ssh, viene allocato un numero locale per il canale e in seguito si deve spedire il messaggio della seguente forma

```cpp
byte SSH_MSG_CHANNEL_OPEN
string channel type   # tipo dell'applicazione
uint32 sender channel # numero locale del canale 
uint32 initial window size # bytes dei dati che possono essere inviati senza modificare la finestra
uint32 maximum packet size # byte massimi di un singolo pacchetto da spedire al sender
```

### Esempio scambio di messaggi del connection protocol

![[Pasted image 20251106142242.png]]

Se la parte remota è in grado di aprire il canale, restituisce un messaggio SSH_MSG_CHANNEL_OPEN_CONFIRMATION, che include il numero del canale mittente (sender channel number), il numero del canale destinatario (recipient channel number), e i valori della finestra (window) e della dimensione del pacchetto per il traffico in entrata. Altrimenti, la parte remota restituisce un messaggio SSH_MSG_CHANNEL_OPEN_FAILURE con un codice di errore che indica il motivo del fallimento.

Una volta che un canale è aperto, il trasferimento dei dati viene eseguito utilizzando un messaggio SSH_MSG_CHANNEL_DATA, che include il numero del canale destinatario e un blocco di dati. Questi messaggi, in entrambe le direzioni, possono continuare finché il canale è aperto.

Quando una delle due parti desidera chiudere un canale, invia un messaggio SSH_MSG_CHANNEL_CLOSE, che include il numero del canale destinatario.

### Tipi di canali

i canali possono essere:
- **Session**
	consiste nell'esecuzione remota di un programma che può essere una shell,un'applicazione come email o trasferimento dei file o un comando di sistema. Quando una sessione è stata aperta, le eventuali richieste sono usate per partitre il programma in remoto 
- **X11**
	fa riferimento al [ sistema X window ](https://it.wikipedia.org/wiki/X_Window_System) , che fornisce una gui per computer in rete. Le applicazioni vengono fatte girare sulla rete dei server, ma la lora visualizzazione è mostrata nelle macchine desktop 
- **Forwarded-tcpip**
	fa port forwarding in remoto. Il client SSH dell'utente agisce per conto del server. Il client riceve il traffico su un numero di porta dato di destinazione, posiziona (inoltra) il traffico sulla porta corretta e lo invia alla destinazione scelta dall'utente. Un esempio tipico di inoltro remoto è il seguente: desideri accedere a un server di lavoro dal tuo computer di casa. Poiché il server di lavoro si trova dietro un firewall, non accetterà una richiesta SSH proveniente dal tuo computer di casa. Tuttavia, dall'ufficio puoi configurare un tunnel SSH utilizzando l'inoltro remoto.
- **Direct-tcpip**
	fa port forwarding in locale che permette di setuppare un proccesso di hijacker. In pratica intercetta il traffico a livello di applicazione e lo reinderizza da una connessione non sicura TCP ad un tunnel SSH sicuro. Bisogna configurare dall'inizio quali porte interessata da sorvegliare
