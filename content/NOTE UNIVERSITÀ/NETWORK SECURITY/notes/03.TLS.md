Il tls è un'evoluzione diretta del protocollo SSL (Secure Sockets Layer) che è stato sviluppato da Netscape. TLS è un servizio general purpose implementato come un insieme di protocolli che si affidano su TCP. Ci sono due implementazioni disponibili di TLS:

- Il TLS (Transport Layer Security) potrebbe essere fornito all'interno della suite di protocolli di base ed essere quindi trasparente per le applicazioni.
- l TLS può essere integrato (embedded) in pacchetti specifici. Ad esempio, la maggior parte dei browser è dotata di TLS (viene fornito con TLS), e la maggior parte dei server Web ha implementato il protocollo.

Ci sono tre componenti principali per ciò che il protocollo TLS realizza
- **Crittografia**: 
	nasconde i dati trasferiti da terzi.
- **Autenticazione**: 
	garantisce che le parti che si scambiano informazioni siano davvero chi affermano di essere.
- **Integrità**: 
	verifica che i dati non siano stati contraffatti o manomessi.

### Architettura TLS

Come già detto, tls è stato progettato per fare uso di TCP per fornire un servizio di sicurezza end to end. TLS non è un singolo protocollo, ma sono due livelli di protocolli.

![[Pasted image 20251027132723.png]]

Il TLS Record Protocol fornisce servizi di sicurezza di base a vari protocolli di livello superiore. In particolare, l'Hypertext Transfer Protocol (HTTP), che offre il servizio di trasferimento per l'interazione client/server Web, può operare sopra al TLS.

Tre protocolli di livello superiore sono definiti come parte integrante del TLS: l'Handshake Protocol; il Change Cipher Spec Protocol; e l'Alert Protocol. Questi protocolli specifici del TLS sono utilizzati nella gestione degli scambi TLS e verranno esaminati più avanti in questa sezione.

Un quarto protocollo, l'Heartbeat Protocol, è definito in una RFC (Request for Comments) separata e sarà anch'esso discusso successivamente in questa sezione.

### Connessione e sessione TLS

due concetti importanti di tls sono la **connessione** e **sessione**

- **Connessione**
	è un trasporto che fornisce un tipo di servizio adatto. Le connessione in TLS sono relazioni peer-to-peer. Le connessioni sono transitorie (o temporanee). Ogni connessione è associata a una sessione. Significa che le connessioni sono di breve durata e non permanente, perchè una connessione viene stabilita solo per il tempo necessario
- **Sessione**
	una sessione TLS è un'associazione tra il client e il server per mettesi d'accordo su informazioni di sicurezza (ad esempio algoritmi di cifratura ecc. ecc.). Le sessioni vengono realizzate dal Handshake Protocol, in seguito alla creazione della sessione il server e il client condividono la Master key. La sessione quindi lo si fa una sola volta

Ogni conessione TSL ha uno stato ed è definito dai seguenti parametri:

- **Server and client random (Valori _random_ del server e del client):** Sequenze di byte scelte dal server e dal client per ogni connessione.
    
- **Server write MAC secret (Segreto MAC di scrittura del server):** La chiave segreta utilizzata nelle operazioni MAC (_Message Authentication Code_) sui dati inviati dal server.
    
- **Client write MAC secret (Segreto MAC di scrittura del client):** La chiave simmetrica utilizzata nelle operazioni MAC sui dati inviati dal client.
    
- **Server write key (Chiave di scrittura del server):** La chiave di crittografia simmetrica per i dati crittografati dal server e decrittografati dal client.
    
- **Client write key (Chiave di scrittura del client):** La chiave di crittografia simmetrica per i dati crittografati dal client e decrittografati dal server.

- **Initialization vectors (Vettori di inizializzazione):** Quando viene utilizzata una cifratura a blocchi in modalità CBC (_Cipher Block Chaining_), viene mantenuto un vettore di inizializzazione (IV) per ogni chiave. Questo campo viene inizializzato per la prima volta dal Protocollo di Handshake TLS. Successivamente, il blocco finale di testo cifrato di ciascun record viene conservato per essere utilizzato come IV con il record successivo.
    
- **Sequence numbers (Numeri di sequenza):** Ciascuna parte mantiene numeri di sequenza separati per i messaggi trasmessi e ricevuti per ogni connessione. Quando una parte invia o riceve un _"change cipher spec message"_, il numero di sequenza appropriato viene impostato a zero. I numeri di sequenza non possono superare $2^{64} - 1$.


Ogni sessione TSL ha uno stato ed è definito dai seguenti parametri:

- **Session identifier (Identificatore di sessione):** Una sequenza arbitraria di byte scelta dal server per identificare uno stato di sessione attivo o ripristinabile (resumable).
    
- **Peer certificate (Certificato del peer):** Un certificato X.509.v3 dell'interlocutore (_peer_). Questo elemento dello stato può essere nullo.
    
- **Compression method (Metodo di compressione):** L'algoritmo utilizzato per comprimere i dati prima della crittografia.
    
- **Cipher spec (Specifica di cifratura):** Specifica l'algoritmo di crittografia dei dati di massa (_bulk data encryption algorithm_) (come _null_, AES, ecc.) e un algoritmo di _hash_ (come MD5 o SHA-1) utilizzato per il calcolo del MAC (Message Authentication Code). Definisce anche attributi crittografici come la dimensione dell'hash (_hash_size_).
    
- **Master secret (Segreto principale/Master secret):** Un segreto di 48 byte condiviso tra il client e il server. Se questa chiave venisse compromessa, l'attaccante riuscirebbe a compromettere tute le altri chiavi.
    
- **Is resumable (È ripristinabile/Può essere ripreso):** Un _flag_ che indica se la sessione può essere utilizzata per avviare nuove connessioni.

### Record Protocol TLS

Questo protocollo fornisce due servizi per le connessioni TLS:
- **Confidenzialità**
	L'Handshake protocol definisce una chiave segreta condivisa che viene usata per crittrografia convenzionale per i payload TLS.
- **Messaggio d'integrità**
	L'Handshake protocol definisce anche una chiave segreta condivisa che viene usata per creare un MAC (Message Authentication Code).

![[Pasted image 20251029154958.png]]

Il protocollo prender un messaggio che deve transmettere, lo frammenta in piccoli blocchi, opzionalmente comprime i dati, ci applica un mac, cripta, aggiunge l'header e trasmette questa unità finale in un segmento TCP. Con questo processo i dati ricevuti devono essere decodificati, verificati, decompressi e riassemblati prima di essere consegnati all'utente al livello superiore.

### Change cipher spec protocol

Questo protocollo consiste in un singolo messaggio che risulta essere un byte. L'obiettivo di questo byte è quello di copiare lo stato di pending nello stato corrente, il quale aggiorna la suite cipher e le nuove chiavi negoziate da utilizzare dei prossimi record nella connessione. In parole povere, serve per notificare che si vuole cambiare il sistema crittografico tra client e server 


---
### Alert protocol

Questo protocollo viene usato per convogliare avvisi relativi al TLS all'entità peer della connessione, sono sostanzialmente delle notifiche a eventi. Questi messaggi di avvisi sono compressati e cirptati. Ogni messaggio è composto da due byte

- il primo byte prende il valore attenzione (1) o fatale (2) per informare la serverità del messaggio. Se il valore è fatale TLS termina immediatamente la connessione. Altre connessioni sulla stessa sessione possono continuare ma non ci saranno più altre nuove connessioni nella stessa sessione.
- il secondo byte contiene un codice che indica il tipo di alert specifico

reference : https://www.gnutls.org/manual/html_node/The-TLS-Alert-Protocol.html

### Handshake protocol

È il protocollo più complesso di TLS, che abilita al server e al client di autenticarsi a vicenda e di negoziare un sistema crittografico e algoritmo del MAC usati per lo scambio di informazioni in modo sicuro tra le due entità nel record TLS.
Come si intuisce, è una fase che avviene prima dello scambio di messaggi. Il protocollo consiste in uno scambio di messaggi tra il client e server in modo bidirezionale. Ogni messaggio ha tre campi
- **Tipo (1 byte)**
	indica uno dei tipi dei messaggi seguenti (colonna sinistra)

| tipo messaggio      | Parametri                                                   |
| ------------------- | ----------------------------------------------------------- |
| hello_request       | null                                                        |
| client_hello        | version,random,session id, cipher suite, compression method |
| server_hello        | version,random,session id, cipher suite, compression method |
| certificate         | chain of x.509v3 certificates                               |
| server_key_exchange | parameters, signature                                       |
| certificate_request | type, authorities                                           |
| server_done         | null                                                        |
| certificate_verify  | signature                                                   |
| client_key_exchange | parameters, signature                                       |
| finished            | hash value                                                  |

- **Lunghezza (3 byte)**
	lunghezza del messaggio in bytes
- **Contenuto (>= 0 bytes)**
	contiene i parametri associati ai tipi di messaggi visti prima (colonna destra)

| tipo messaggio      | Parametri                                                   |
| ------------------- | ----------------------------------------------------------- |
| hello_request       | null                                                        |
| client_hello        | version,random,session id, cipher suite, compression method |
| server_hello        | version,random,session id, cipher suite, compression method |
| certificate         | chain of x.509v3 certificates                               |
| server_key_exchange | parameters, signature                                       |
| certificate_request | type, authorities                                           |
| server_done         | null                                                        |
| certificate_verify  | signature                                                   |
| client_key_exchange | parameters, signature                                       |
| finished            | hash value                                                  |
Lo scambio di informazioni per stabilire una connessione sicura avviene in 4 fasi

![[Pasted image 20251029164545.png]]

- **FASE 1**
	In questa fase il client e il server iniziano ad approcciarsi per inizializzare una connessione  e cercando di stabilire le capacità di sicurezza associato ad esso. Lo scambio parte sempre dal client, il quale manda un messaggio in chiaro di *client_hello message* (con gli eventuali parametri visti prima). In sostanza il client vuole creare una connessione con il server e gli offre le sue capacità crittografiche. Il server cerca di prendere il meglio di quello che è stato offerto dal client, in seguito il client aspetta il messaggio in chiaro di *server_hello message* (con gli stessi parametri di *client_hello*) dal server, che propone al client una suite crittografica. I messaggi sono in chiaro perchè tanto la cosa veramente da proteggere è la chiave segreta

- **FASE 2**
	Ora il server deve autenticarsi al client, cioè deve dimostrare al client di essere lui veramente. Lo fa mandando il suo certificato con il messaggio *certificate* (non previsto se viene scelto anonymous diffie-hellman). Successivamente il sever può mandare al client il messaggio *server_key_exchange*, solo se è richiesto, perchè ci sono due istanze in cui questo scambio di chiave non serve ed è quando se
	- il server  ha mandato un certificato con diffie-hellman fissato nei parametri
	- il metodo di scambio di chiavi usato è RSA
	Il server può anche fare una richiesta del certificato del client (opzionale). L'ultimo messaggio obbligatorio di questa fase è il messaggio di *server_hello_done* (non ha parametri) inviato dal server per dare conferma al client. Ora il server si aspetta una risposta dal client.
